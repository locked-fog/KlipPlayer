# 定点预览与同步验收

这些命令使用与 `play` 相同的解析、编译和 ANSI 渲染路径；不改变 `.klip`
格式。以下示例从仓库根目录运行。

## 检查事件和画面

```sh
cargo run -- inspect --at 03:16.197 --window 500ms examples/netsu-ijou.klip
cargo run -- render --at 03:16.525 examples/netsu-ijou.klip
```

`inspect` 输出指定时间前后各 500 ms（含边界）的事件。可用 `--window 0ms`
只看同一时间戳，也可指定整数秒，如 `--window 2s`。输出包含事件顺序、
Z、cursor、保护状态和脚本行号；`music exists` 只检查文件，不打开设备。

`render` 立即执行时间戳之前及该时间戳上的全部事件，不启动音频、不等待。
输出是 ANSI 命令流，可直接在终端查看；退出前恢复文本样式和光标。
它不会生成图像，也不建立另一套画面状态。若终端小于脚本 canvas，
命令会在 stderr 提示；《熱異常》需要至少 160 列 × 40 行。

建议检查这些位置：

| 时间 | 检查内容 |
| --- | --- |
| `00:00.000` | 开场画面、字体与光标状态 |
| `01:27.564` | 副歌切换时同一毫秒的 clear、歌词与特效顺序 |
| `03:16.525` | 异常段的背景和受保护歌词 |
| `03:27.022` | 结尾特效的线条、日文与私用区图标 `` |

各时间点先用 `inspect --at <时间> --window 500ms` 查源文件行号，
再用 `render --at <时间>` 看画面；最后用 `play --start-at <时间>`
核对实际演出。`render` 的边界是包含该时刻，`play --start-at` 会先快速
执行更早的事件，再随音频时钟执行该时刻及后续事件。

## 记录内部同步数据

```sh
cargo run -- play --start-at 03:16.197 \
  --sync-report /tmp/klip-abnormal-01.tsv examples/netsu-ijou.klip
```

选择一个新的报告文件路径；命令拒绝覆盖现有文件。正常结束或按 Ctrl-C
后会写出 TSV。`clock=audio` 表示音频设备路径已启动，`clock=fallback`
表示使用无音频时钟。`preload` 行是跳转前立即重放的事件，没有内部延迟
数值；`timed` 行记录事件的计划时间与 ANSI flush 完成后的播放时钟。
音频结束后如仍有脚本事件，播放时钟由单调时钟继续推进。
头部的 `max_dispatch_delay_ms` 和 `p95_dispatch_delay_ms` 只描述内部
派发，**不能当作扬声器发声到屏幕显示的实际偏差**。报告不包含音频，
但包含脚本的 source 标识和行号，按需要保存在仓库外。

## 目标机器验收

在 Linux、Windows、macOS 上各选一款实际使用的终端和一个音频设备：

1. 设置至少 160×40，分别运行上表四个 `render` 时间点，检查颜色、
   擦除、Z 保护、日文宽度和结尾私用区图标。再缩小终端，确认尺寸警告。
2. 用真实音源从四个时间点 `play --start-at`，对照相应的 `render`
   画面，观察是否有稳定的提前、滞后或随时间增长的漂移。
3. 每段各跑至少三次，保留不同文件名的同步报告，同时记录终端、
   字体、音频设备、主观观察和必要的外部音画测量。
4. 在播放中按 Ctrl-C，确认声音停止、光标和样式恢复，并检查报告
   已写入。缺失音源时确认 warning 和 `clock=fallback`。

本地 Linux 检查已覆盖 80×24/160×40 伪终端警告与恢复，以及真实音源
从 `03:16.197` 跳入后约两秒的音频时钟报告。它们不代替其他平台的
实机终端和听觉验收。只有重复测量出现稳定偏差时，才应定义并实现
设备/终端相关的可配置校准值。
